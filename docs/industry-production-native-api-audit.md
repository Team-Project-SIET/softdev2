# OpenTTD 15.3 industry production native API audit

This document audits the exact `15.3` tagged source. It adds no protocol or implementation. Native launches, live Admin connections and real requests: **0 / 0 / 0**. Production bindings have been source-verified, not exercised in a new native proof.

## Binding authority

The tagged [API build rules](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/script/api/CMakeLists.txt#L38-L65) select `game;GS`. The [Squirrel export generator](https://github.com/OpenTTD/OpenTTD/blob/15.3/cmake/scripts/SquirrelExport.cmake#L316-L348) replaces the `Script` class prefix with `GS`, and [registers static methods using their exact original names](https://github.com/OpenTTD/OpenTTD/blob/15.3/cmake/scripts/SquirrelExport.cmake#L478-L484). These establish the names below rather than assuming AI-to-GS naming equivalence. The generator was inspected; this audit did not compile OpenTTD or run its generated bindings. `GetProductionLevel` is marked `@api -ai`: it is available to GameScript, not AI.

The [industry implementation](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/script/api/script_industry.cpp#L75-L121), [remaining getters](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/script/api/script_industry.cpp#L198-L278) and [API documentation](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/script/api/script_industry.hpp) define these cases. No ScriptIndustry getter exposes current-month production, cargo-specific internal production rate, output waiting, the internal valid-history mask or arbitrary older-month production.

Type-level APIs map `ScriptIndustryType` to `GSIndustryType`: `IsValidIndustryType`, `IsRawIndustry`, `IsProcessingIndustry`, `ProductionCanIncrease`, `GetProducedCargo`, `GetAcceptedCargo`. They describe classification, eligible structural cargoes and an increase-permission property; none returns guaranteed capacity. `ProductionCanIncrease` checks landscape and the type's no-increase behavior, not a forecast of callback outcomes. [Tagged type implementation](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/script/api/script_industrytype.cpp#L25-L92).

## What production and transported actually count

Native industry production first accumulates output waiting. When output is released to nearby station distribution, the current-month production counter gains the released quantity, with recession reduction applied first. The transported counter gains the amount allocated to station waiting cargo by `MoveGoodsToStation`. It does **not** count vehicle pickup, journey completion or delivered destination cargo. Station ratings, eligible stations, exclusivity and allocation affect it. [Industry release](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/industry_cmd.cpp#L517-L542), [station distribution](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/station_cmd.cpp#L4599-L4681), [station waiting allocation](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/station_cmd.cpp#L4401-L4417).

The internal monthly production and transported fields are independent unsigned 16-bit counters, each 0..65535; their additions are not saturated. The percentage uses zero for zero production, otherwise clamps `transported * 256 / production` to 0..255, then computes `value * 101 >> 8` to return 0..100. Consequently, percentage is rounded/clamped native service metadata, not an exact floating quotient. A universal `transported <= production` validator is unsafe: independent counter wrap and station fractional allocation mean the raw counters do not provide an unrestricted mathematical invariant. A restricted low-volume fixture may assert the relationship under its frozen assumptions, but a generic NewGRF-compatible protocol must not silently impose it. [Storage and ratio](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/industry.h#L62-L83), [percent conversion](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/core/math_func.hpp#L280-L289).

## Fresh-world and rollover behavior

Map generation is a special case: the engine seeds `LAST_MONTH.production` with cargo-scaled estimates. A Production256Ticks callback can contribute waiting output multiplied by eight; default/current rate multiplied by eight is also added. Output waiting is cleared after the callback contribution. This can yield non-zero previous-month values immediately despite no observed month having elapsed. It is initialized history, not measured elapsed production. Transported history starts zero. Normal gameplay-created industries start default-zero history instead; zero must not be equated with absent production capability. [Initialization](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/industry_cmd.cpp#L1772-L1855).

Before rollover, last-month getters continue returning the seeded/default previous slot while current-month counters accumulate separately. At each economy-month boundary, `UpdateIndustryStatistics` rotates current-month counters into last-month and clears the new current slot. The first boundary therefore replaces seeded history with the observed interval since creation, which can be only a partial month. After two observed boundaries, the immediately preceding interval is a full economy month for industries that existed throughout it. Later boundaries keep shifting history; these getters expose only the most recent slot. [Monthly rotation](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/industry_cmd.cpp#L2563-L2585), [rotation mechanics](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/misc/history_func.hpp#L41-L54).

There is no public Boolean “history valid” getter. A valid zero can mean genuinely no credited output, no input deliveries at a processing industry, no production interval yet, or initialized zero. Invalid industry/cargo/not-produced is separately detected by validity/capability checks and -1 return values. Level zero can signal scheduled closure for a still-valid industry; invalid also returns zero, so industry validity must be checked independently. Monthly processing updates statistics, deletes closure-level industries and evaluates production changes. [Monthly owner](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/industry_cmd.cpp#L3128-L3142).

## Economy time and capacity limitations

`ScriptDate::GetCurrentDate` maps to **`GSDate.GetCurrentDate`** and reads economy date. `GSDate.GetYear`, `GetMonth`, `GetDayOfMonth` and `GetDate` use economy conversion. There is no invented `GSEconomyTime` binding. Date storage is signed 32-bit; a conservative valid-date serialization bound uses ten decimal digits. `GSIndustry.GetConstructionDate` returns calendar date instead: do not subtract it from economy dates in wallclock mode. [Date implementation](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/script/api/script_date.cpp#L23-L61), [date representation](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/timer/timer_game_common.h#L34-L35).

In calendar timekeeping, economy and calendar use Gregorian months. In wallclock timekeeping economy uses twelve 30-day months/360-day years; calendar progression can differ or halt. Production and statistics follow economy time. The API documents one economy-month per realtime-minute in wallclock mode, subject to running rather than paused simulation; real elapsed waiting is not a robust completion authority. Economy day progression uses 74 simulation ticks; the default game tick target is 27ms, but speed/performance/pauses affect real elapsed duration. Economy variables update before day/month/year timers execute. Read bracketing must avoid collection across an economy-month change. [Time API documentation](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/script/api/script_date.hpp#L27-L51), [economy timer](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/timer/timer_game_economy.cpp#L123-L177), [tick constants](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/timer/timer_game_tick.h#L75-L76), [tick target](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/gfx_type.h#L370).

`GSController.GetTick` is source-exported, but returns the script controller's own tick counter, not a replacement economy-month identity. [Controller export](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/script/api/game/game_controller.sq.hpp#L17), [getter](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/script/api/script_controller.cpp#L77-L80).

Production level is dimensionless: default16, supported production-setting range4..128, zero closure. Original-economy rates are computed from type rate times level divided by16 and clamped to an 8-bit per-cargo rate. Smooth production and callbacks undermine treating that level as a universal units/month conversion. Internal regular output occurs every256 ticks, scaled by cargo-production settings; callback intervals can themselves be scaled. No public cargo-specific rate getter exists. [Level constants](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/industry.h#L35-L38), [rate recomputation](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/industry_cmd.cpp#L2589-L2600), [production timing](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/industry_cmd.cpp#L1148-L1194).

## Reproducibility and future meaningful proof

Freeze seed/world/profile; landscape and generation settings; industry types and cargo scale; economy original/smooth and recession settings; economy timekeeping and speed/pause policy; all NewGRF IDs/content/parameters/callback behavior; external GameScript/AI/company activity and industry control flags. Production changes may be random, transported-percentage-sensitive or callback-defined; closure and spontaneous industry creation can change the source set. The current level and last month's output are observations, not guaranteed future capacity. [Production changes](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/industry_cmd.cpp#L2876-L3038), [daily industry changes](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/industry_cmd.cpp#L3086-L3120), [callback economy selection](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/industry_cmd.cpp#L3222-L3238).

For a future read-only non-zero proof, observe two economy-month boundaries after generation, then collect the previous full month from existing producing industries. Require at least one positive result only for a frozen profile with source-justified input-independent production; do not require every industry to be positive. An unserved processing industry may correctly remain zero. Retain boundary evidence, source capability membership, native API errors and one unchanged economy year/month across collection. Do not warm up by constructing service or injecting inputs. Warm-up does not make the dynamic snapshot atomic and can increase industry drift; recollect structural data after warm-up rather than trusting pre-warm-up industry IDs.
