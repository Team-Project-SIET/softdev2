# OpenTTD 15.3 road vehicle lifecycle proof

Current milestone: **ROAD VEHICLE LIFECYCLE PROVEN**, native Attempt 2. Freight delivery remains unproven.

This bounded proof loads a disposable copy of the independently verified road freight infrastructure save. It preserves the original save and evidence. It permits one process, one secure Admin connection, twelve requests and three mutations: purchase, append one truck-stop order, and start. There are no retries or reconnects.

The bridge selects the lowest available compatible non-articulated road engine using native engine enumeration. Its default cargo, capacity, price and test-mode purchase cost must agree. This proof performs no refit. Actual purchased capacity and company ownership are checked independently. Every mutation has fresh native admission; failed admission stops the runner.

The implementation follows the tagged [15.3 engine API](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/script/api/script_engine.hpp), [vehicle API](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/script/api/script_vehicle.hpp), and [order API](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/script/api/script_order.hpp). A successful test-mode BuildVehicle returns zero; the real vehicle ID requires native validation. The single order targets the existing truck stop with OF_NONE.

Before launch, the seal binds source and packaged script hashes, original infrastructure receipt and save, copied save, runtime, command, engine-selection policy, budgets and cleanup. Native observations then bind the exact engine and final plan. Readbacks verify purchase, exact order, started state and a location outside the depot within a bounded observation interval. Movement does not prove freight delivery.

The offline receipt verifier replays all admissions and transitions, checks retained Admin frames and save identities, and requires process, endpoint and credential cleanup. Application responses remain at most 512 bytes; GSAdmin messages remain within 1450 bytes.

Controlled verification: 29 lifecycle tests and 192 focused regression tests passed. The ordinary serial suite passed with 3,724 passes, 48 skips and 3 native tests deselected. Scoped Ruff, formatting, typecheck and whitespace checks passed.

## Offline movement-gate correction

The old gate counted thirty `Sleep(1)` calls, sampled before each sleep, and retained neither clock values nor pause state. Calling this thirty observed **game ticks** was incorrect. [GSController.Sleep](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/script/api/script_controller.hpp) uses script ticks. [StateGameLoop](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/openttd.cpp) continues GameScript execution while paused but skips vehicle ticks. [GSGame.IsPaused](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/script/api/script_game.cpp) checks native pause flags. No unpause command is introduced.

[RoadVehLeaveDepot](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/roadveh_cmd.cpp) resets speed to zero and starts at depot frame 6; road movement must reach the next-tile marker at frame 16. RUNNING describes a vehicle that is not stopped, crashed, broken or loading; it does not mean it has left its tile. `IsInDepot` in the script API means **stopped in depot**, whereas [GetLocation](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/script/api/script_vehicle.cpp) returns the native road vehicle tile. The exposed vehicle API supplies no sub-tile x/y readback. Tile transition therefore remains the proof criterion.

The bound has a concrete motion-scale justification. In the original acceleration model, [DoUpdateSpeed](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/ground_vehicle.hpp) increases internal speed by one each vehicle tick; [GetAdvanceSpeed/GetAdvanceDistance](https://github.com/OpenTTD/OpenTTD/blob/15.3/src/vehicle_base.h) contribute `floor(3*speed/4)` progress and require 192 progress units per diagonal movement step. With a speed cap of at least 60 internal units, thirty acceleration ticks provide only 337 progress units (one step), while eighty provide 2,250 (eleven steps). Frame 6 to the next tile requires ten steps. These calculations illustrate why thirty ticks cannot reasonably be a universal departure deadline; they are conditional source-derived calculations, not recovered settings or measured positions from Attempt 1. Realistic acceleration, command scheduling and obstruction can change timing.

The corrected budget permits at most **256 elapsed script ticks**, **257 samples** including the initial sample, and **60 wall-clock seconds**, inside the unchanged 180-second lifecycle deadline. The 256-tick cap exceeds the illustrative eighty-tick departure scale by 3.2 times; it is an explicit operational observation budget, not a promise that every vehicle or route departs within it. Polls sleep one script tick, measure actual `GetTick()` values, and fail on stalled/regressing clocks or overshoot. The final sample at exactly the cap may succeed; later transitions cannot. If departure already occurred by the initial sample, its tile is compared with the independently verified purchase-depot baseline.

Each sample independently rereads the vehicle and checks pause state, the company-owned connected stop/road/depot footprint, engine/owner/capacity, running state and exact station order. Success requires a native tile outside the purchase depot and within the verified site. `PAUSED`, `CLOCK_STALLED`, `INVALID_ROUTE`, and `READBACK_MISMATCH` identify observed failed prerequisites. `WINDOW_EXHAUSTED` means no qualifying tile transition within the budget despite sampled valid prerequisites; it does **not** prove path blockage. `MOVEMENT_WALL_DEADLINE_EXPIRED` means observations did not finish and progress is unknown. Speed, RUNNING and script-clock advancement alone never admit success.

The compact motion response carries the original native snapshot as a fixed fifteen-field array and `[first_script_tick,last_script_tick,sample_count,paused]`. The Python parser restores the typed snapshot, preserves request correlation and checks the 512-byte wire bound. Receipt verification additionally requires bounded clock/poll evidence and records its meaning. The future prelaunch profile is v2/Attempt 2 with these exact budgets. The consumed v1 evidence remains unchanged; no Attempt 2 directory, seal, process or Admin connection has been created by this correction.
